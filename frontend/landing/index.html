PROBLEM/// THE READER

Every sealed auction
leaves one
reader standing

To clear a sealed auction, something has to read every bid. Whatever reads them can also lie about them: drop the inconvenient ones, clear at a worse price, leak a number to a friend. Privacy technology has been shrinking that reader for a decade. None of it removes them.

Fig. 1 /// Who still reads the bids
ApproachWhat it guaranteesReader remainingBlind

Homomorphic arithmetic without decryption nobody, but ranking N bids costs more than the trade Partial
Attested enclave correct clearing over a set fixed on-chain nobody. The code hash is public; the key never leaves Yes

Removing the reader,
not shrinking it

The enclave is not a party to the trade. It has no address, no balance, no counterparty. It decrypts, ranks, clears, signs, and forgets. The operator running the machine cannot read a single bid out of it, because the decryption key never leaves attested hardware.

And it cannot be
fed a doctored set

A blind auctioneer is worthless if the caller chooses which bids it sees. Buta's enclave signs over the commitments the contract recorded, so a trimmed set fails verification on-chain. Suppressing the Vickrey uplift stops being a policy promise and becomes an arithmetic impossibility.

SEQUENCE/// CLEARING

Four steps.
One impossible
anywhere else

Encrypt

Bid to a key
nobody holds

ECIES-encrypted under the enclave's public key, read from GET /info. The matching private key exists only inside attested hardware.

Commit

The chain
records the set

One commitment per sealed bid lands on Flare. The clearing set is fixed before anyone knows what is in it, so it cannot be trimmed later.

Clear

Second price,
computed blind

At the deadline the enclave decrypts, ranks, and clears at the Vickrey price, signing over the commitments the contract recorded, not a set the caller supplied.

Settle

FXRP,
then XRPL

The contract recovers the enclave signature and settles in FXRP. The lot moves to the winner, redeemable to native XRP.

Only the clearing step needs the enclave. Encrypt, commit and settle are ordinary Flare contract work, which is exactly why the trust story holds.

DELTA/// AGAINST REFERENCE

Past Flare's own
confidential
orderbook

Buta forks fce-orderbook, Flare's FCC reference exchange, for vault custody and the signing path, then changes four things it does not do. Two of them the reference flags as open holes in its own documentation.

Bids arrive
as ciphertext

The reference posts orders as plaintext JSON: private from the chain, visible to the proxy operator in transit. Defensible for a continuous book, fatal for a sealed auction. Buta takes the ECIES path.

Requests bound
to a wallet

The reference trusts the sender field at face value and says so. Buta verifies a wallet signature over the bid before any balance is held.

A production deployment must bind the request to a wallet signature. fce-orderbook /// threat model

The bid set is
anchored on-chain

The reference keeps every order in enclave memory and anchors nothing, so a restart loses the book. Commitments fix the clearing set and make it replayable. One decision, two problems.

Settlement crosses
two ledgers

The reference is ERC-20 only. Buta clears in FXRP and delivers a lot that redeems to native XRP, so the winner takes settlement on the ledger the asset came from.
